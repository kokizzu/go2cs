# Background

> "I've been programming in C# for many years, even so, I try to keep an eye on new tech being developed, regardless of language -- one common choice for new applications these days is Go. Often the easiest way for me to experiment with new technology is to integrate it with some of my existing C# code, hence the desire for this project -- besides, I figured I might learn something about building apps in Go in the process."

That was [2018](README.md#milestones), and back then it was mostly a personal itch: I wanted to learn Go by writing it into something I already knew. Eight years and two full converter architectures later, the itch is still here -- but the reasons this thing is worth building have gotten a lot better than "I was curious". More to the point, most of them are now things I can *show* you instead of argue about, so here is the longer answer to *why a Go to C# transpiler?*

## Why convert Go to C#?

**Integration -- using Go code from inside .NET.** Plenty of organizations are standardized on .NET: the build system, the CI, the deployment story, the code review habits, the hiring. When the library they need -- or the Go-originated logic they already own -- happens to be written in Go, the usual choices are to run it as a separate process, wrap it behind a C ABI, or reimplement it by hand and maintain two copies forever. go2cs aims at a fourth option: convert it and reference it like any other .NET assembly. That comes in two shapes:

* *Consume a Go library.* The converted standard library, the `golib` runtime and the source generators are published on nuget.org as [`go.<pkg>` / `go.lib` / `go.gen`](https://www.nuget.org/packages?q=go2cs%20ritchiecarroll) (versioned `1.23.1.<build>` from [`src/version.props`](https://github.com/ritchiecarroll/go2cs/blob/master/src/version.props)), and `go2cs -recurse=nuget` emits a converted project that references them -- so pulling in Go-originated code can look like adding a `PackageReference`.
* *Convert a whole application.* [`-recurse`](README.md#converting-a-real-world-module) converts an app together with every third-party package in its import closure, in dependency order, into a solution you can open and build. The README walks the full round-trip for a small CLI built on `github.com/fatih/color` -- four dependency projects behind it -- and that example compiles **and runs**.

The rough edge, stated plainly: referencing the stack as *compiled packages* rather than source still has gaps in the source generators' cross-assembly path, so source deployment is the route I'd use today (see NOTE 2 in that walkthrough).

**Migration and coexistence -- with fidelity you can measure.** A transpiler whose output merely *compiles* has proven very little, and I've been on the wrong side of that lesson inside this very repo: the [first "full standard library conversion" in 2025](README.md#milestones) meant only that the converter didn't crash. So the currency of correctness here is **Go's own tests**. For a validated package, the real `_test.go` suite is converted to C#, built against the converted standard library, run under a Go-semantics test host, and compared **verdict for verdict** against a clean `go test -json` baseline -- and the package is listed only when every `Test` agrees on both sides and every declaration that isn't executed is accounted for. The current set (dozens of packages, more than a thousand matching verdicts so far) is kept in [Validated Test Packages](ValidatedTestPackages.md); it grows as packages land, and it publishes its own denominator -- the converted packages whose Go 1.23.1 sources actually define tests -- rather than a flattering one. Underneath that sit roughly 500 [behavioral test projects](https://github.com/ritchiecarroll/go2cs/tree/master/src/Tests/Behavioral): each a small Go program, transpiled, compiled, byte-compared against a committed golden and, where it's a runnable program, executed with its stdout compared against the Go original's. This is the argument I care most about, because "syntax converter" and "passes the source language's own test suites, verdict for verdict" are different classes of claim -- and the second one is [reproducible from a clone with one command](README.md#try-it-yourself--validate-a-converted-test-suite). That is what turns gradual migration from a leap of faith into a plan: move a package at a time, and keep the receipts.

**Deployment reach -- .NET as another place Go source can run.** A Go program usually ships as a single self-contained native binary, and that's a reasonable thing to want to keep. Published with **Native AOT**, converted C# gets close on the axis that matters for CLI-shaped programs: in the [current measurements](Performance.md) an AOT build starts in ~17 ms against Go's ~13 ms at a few MB of working set, where the JIT build pays ~39 ms and ~18 MB. For long-running services the JIT is the better bet -- it wins the tight-loop rows AOT gives up -- and the map benchmark is *faster* than Go in both C# columns, since `map<K,V>` rides .NET's heavily-optimized `Dictionary`. None of which makes converted code uniformly fast: string-heavy work runs roughly 9-11× Go's time today, and the one row measuring interface satisfaction resolved *structurally at run time* -- the thing C# has no native equivalent for -- sits at ~41× on the JIT and worse under AOT. It's all in the table with its methodology, and the runner refuses to time anything until all three binaries produce identical output.

**Readability, so conversion isn't a one-way door.** The output is meant to be *read*. Receiver methods become extension methods, multiple returns become tuples, embedded structs become promoted fields, and the machinery that supplies Go's semantics -- the `golib` runtime and a set of Roslyn source generators -- stays out of sight in partial and generated files. [Conversion Strategies](ConversionStrategies.md) maps this construct by construct, and the README's [side-by-side table](README.md#real-standard-library-conversions-side-by-side) puts real converted standard-library files next to their Go originals so you can judge it yourself. This matters practically as much as aesthetically: if converted code is legible, a team can adopt it and *maintain* it -- fix a bug in the C# on a Tuesday afternoon -- instead of being locked into re-running a transpiler forever, or owning a pile of machine output nobody can review.

That said, the tranpile step is fast and cheap -- technically this code allows one to "_code in Go, run in .NET_", unto here unheard of...

**Learning and reference.** Because the two languages are mapped construct for construct, the output doubles as a translation dictionary for developers crossing between them. [Tour of go2cs](https://github.com/ritchiecarroll/go2cs/blob/master/src/tour/README.md) puts the official Tour of Go on one side of the window and the generated C# on the other, live, with buttons to transpile, build and run the .NET side. That's the tool I wanted for myself in 2018.

**Honest engineering, which is the only reason to trust any of the above.** A tool like this is worth exactly as much as its worst *undisclosed* defect, so I'd rather publish the defects. When a Go test asserts something a managed runtime provably cannot deliver -- an exact allocation count, say, where Go's compiler stack-allocates and the managed runtime must heap-allocate -- the test isn't quietly skipped: the divergence is pinned by exact failure signature in a hand-owned, repo-committed [`go2cs_test_disclosures.json`](https://github.com/ritchiecarroll/go2cs/blob/master/src/go-src-converted/bytes/go2cs_test_disclosures.json), so any *other* failure of that test is still a hard mismatch. Bugs that would bite an end user get written up in the open, severity first -- for instance [a rename defect that broke every converted program using `time.Second`](https://github.com/ritchiecarroll/go2cs/blob/master/docs/Phase4/FINDING-cross-package-collision-rename.md), filed and then updated with its fix and proof. And when a published performance number turns out to be measuring a bug rather than a construct, the superseded table stays [alongside the corrected one](Performance.md#history): one interface row was published at 158× Go, root-caused to two runtime defects, and now reads about 6×. Nothing here is graded on a curve.

**What isn't true yet.** All 302 packages of the converted standard library compile as .NET assemblies (since [2026-07-10](README.md#milestones)) -- but *compiling is not the same as working*, and I try never to blur the two. Making the library operational is the ongoing [Phase 4](Roadmap.md#phase-4--convert-and-run-go-package-tests) effort, and the validated-package table is the honest measure of how far that has gotten. The converted library reproduces Go built with `-tags purego`, since a managed runtime cannot execute Go's hand-written assembly and the portable pure-Go paths are therefore the faithful target. Converted code is generally slower than Go, which is expected, and explained next. If any of that changes, this page and the tables it links are where it will show up.

For those of you that code in Go all the time and have an occasion where you need to build a C# app, this conversion tool is meant to give you a head start: pull in some of your existing code, and keep using the standard library functions you're used to.

## Converted Code

**`TL;DR`**: Do not expect converted C# code to run as fast as the original Go code.

The .NET runtime environment is very different from Go -- a compiled .NET application actually consists of an abstract byte-code based instruction set called [Common Intermediate Language](https://en.wikipedia.org/wiki/Common_Intermediate_Language) (CIL). At runtime the CIL code is compiled to native machine code using a [just-in-time compilation](https://en.wikipedia.org/wiki/Just-in-time_compilation) process. Compared to Go, which is compiled directly to native machine code, .NET incurs some compile based processing delays at startup. However, you can remove the just-in-time compilation startup delays for a .NET application by pre-compiling the application to native machine code using [native AOT deployments](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/?tabs=windows%2Cnet8) ~~image generation tool in .NET `crossgen`~~.

For this project, the philosophy taken for converted code is to produce code that is very visually similar to the original Go code as well as being as behaviorally close as possible to Go at a purely "source code" level. The focus is to make converted code more usable and understandable to a Go programmer inside of a C# environment without being hyper-focused on optimizations. That doesn't mean your converted code is going to be super slow -- it should run as fast as other comparable .NET applications -- it just may not run as fast as the original Go code. However, because of the simplicity of [Go's design](https://talks.golang.org/2012/splash.slide), converted code may have a natural performance advantage over more traditionally developed C# applications just because of its static nature. You don't have to take my word for the size of the gap, either: the measured spread across a dozen small workloads -- Go, C# on the JIT, and C# published with Native AOT -- is published, methodology included, in the [performance comparison](Performance.md).

If you are looking for a more _binary_ integration, you might consider using native compiled Go code directly within your .NET application. One option would be would be [exporting Go functions](https://golang.org/cmd/cgo/#hdr-C_references_to_Go) as C code, including the C code exports in a DLL and then [importing the functions](https://msdn.microsoft.com/en-us/library/system.runtime.interopservices.dllimportattribute%28v=vs.110%29.aspx) in C#.
